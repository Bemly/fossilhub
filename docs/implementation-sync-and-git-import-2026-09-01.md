# 本地、GitHub、NAS 同步与 Git 历史导入计划

日期：2026-09-01

## 目标

1. 以 NAS 留存的 `2026.08.30-beta.2` 构建归档为证据，恢复丢失的短地址源码、测试和文档。
2. 合并并保留本地尚未提交的完整简体中文界面改动。
3. 从一个已提交且可复现的修订构建 `2026.09.01-beta.1`，使本地 `main`、GitHub `main` 与 NAS 生产代码保持一致。
4. 将本项目 Git 的全部分支、标签和提交历史导入为 NAS 上的 `fossilhub.fossil`，并通过 FossilHub 动态仓库登记发布。

## 已确认的边界

- 不修改 fnOS、`/usr/trim`、nginx、systemd、PostgreSQL 系统库或无关容器。
- 生产仍使用 `/vol1/1000/fossilhub:/data`、端口 `6080` 和既有容器安全参数。
- 新仓库使用短地址 `/repo/fossilhub`，原生 clone/sync 地址为 `/fossil/fossilhub`。
- 新仓库归现有 `warden` 管理，完成导入和校验前保持私有；通过后改为公开，默认分支为 `main`。
- 不把 SSH/sudo 密码、平台密码、会话材料或其他凭据写入源码、归档、命令脚本、日志或文档。
- 所有现存回滚容器和生产数据均保留；任何清理另行列出并等待明确授权。

## 阶段一：恢复并固定源码

1. 校验 NAS 归档的 SHA-256，并在本机临时目录展开，不直接覆盖工作区。
2. 先提交本地七个中文化文件，再机械恢复归档中确有差异的 beta.2 文件。
3. 对恢复后的文件逐一做字节级比较，运行 `git diff --check`、JavaScript 语法检查和可在本机 Tcl 8.5 下执行的测试。
4. 将 beta.2 恢复结果作为独立提交，保留清晰的来源和回退边界。

## 阶段二：发布候选修订

1. 将版本提升为 `2026.09.01-beta.1`，同步 `VERSION`、Docker 构建参数、Compose 和发布说明。
2. 检查完整 Git 历史中的高置信凭据模式和敏感文件名；发现问题即停止公开导入与推送。
3. 检查远端仓库、分支和待推送提交，不使用强制推送。
4. 推送 GitHub `main` 后再次核对远端提交 ID。

## 阶段三：本地 Git 到 Fossil 转换验证

1. 从最终发布修订运行 `git fast-export --all`，保留全部分支、标签和提交。
2. 先创建临时空 Fossil 仓库，再使用 `fossil import --git --incremental` 导入，验证该流程不会改变已有 project-code。
3. 禁用导入仓库的 autosync，清空导入管理员能力，并按公开仓库策略设置 `nobody`、`anonymous` 能力。
4. 验证 `fossil test-integrity --quick`、分支、标签、时间线、文件树、最新提交、仓库大小和 0600 权限。

## 阶段四：NAS 隔离候选

1. 使用 `git archive` 生成 NAS 构建输入，OCI revision 标签写入完整提交 ID。
2. 在 NAS 构建镜像，运行镜像内 Tcl 9.1b0 全套测试和真实 Argon2 测试。
3. 精确复制生产数据到独立候选目录；确认端口 `6082` 空闲后启动唯一命名的 `fossilhub-beta-*` 容器。
4. 在候选数据中以私有仓库创建流程登记 `fossilhub`，再离线增量导入 Git fast-export；完整性通过后改为公开并重建目录。
5. 验证首页、Explore、短地址、旧地址跳转、仓库各栏目、clone/sync、挂载前缀、文件权限、运行用户和容器安全参数。

## 阶段五：生产事务式同步与导入

1. 切换前再次核对生产容器、镜像、端口、挂载、回滚名、健康状态和候选结果。
2. 为平台数据库、目录数据库和本次新增仓库建立精确、独立的生产前备份；记录校验和，不覆盖历史备份。
3. 将旧生产容器改为唯一回滚名并停止 HTTP 服务。
4. 在相同数据挂载上登记私有 `fossilhub` 仓库，离线导入 Git 历史，执行完整性检查、权限收敛、公开可见性切换和目录重建。
5. 以同一安全参数启动新生产容器并等待健康；任一步失败时，删除本次未完成的新仓库状态、恢复精确备份并启动原容器。
6. 生产复验健康、核心路由、`/repo/fossilhub`、`/fossil/fossilhub` clone/sync、Git/Fossil 历史对应关系、数据库 quick-check、0600 和 UID/GID 10001:10001。

## 阶段六：交接与收口

1. 更新 `AGENTS.md`、`README.md`、`PLAN.md`、`docs/operations.md`、`docs/releases.md` 和新的生产验收记录。
2. 文档明确区分镜像代码修订与部署后文档修订；再次推送 GitHub 并核对远端。
3. 最终报告本地、GitHub、NAS 镜像、生产容器、Fossil 仓库、回滚容器和备份状态，不输出任何凭据或敏感日志。

## 验收标准

- 本地工作区只保留原有用户文件，不存在未解释的源码差异。
- GitHub `main` 包含完整恢复和新版本提交，且远端提交可精确解析。
- NAS 生产镜像来自已提交修订，OCI revision 为完整 Git 提交 ID，容器健康且安全参数不退化。
- `fossilhub.fossil` 可在短地址浏览并通过原生端点 clone/sync；完整 Git 历史、分支和标签已经导入。
- 新仓库、平台数据库和目录数据库均通过完整性检查，文件保持 0600、UID/GID 10001:10001。
- 旧生产容器、历史回滚容器和生产前备份全部保留，具备明确恢复路径。
